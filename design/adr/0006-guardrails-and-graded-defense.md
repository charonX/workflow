# ADR 0006: 承重墙固化与防线分级（待试用验证）

## Status

Accepted（决策框架，2026-08-06）。

其中"**四道承重墙固化**"立即生效（不可配置）；"候选减项"与"防线分级"记录为留账，待用户实际试用一段时间后，由后续 ADR 决定是否落地。

## Context

ADR 0005 落地"快速收敛"后，继续讨论了快速收敛会不会滑向"AI 自己验收自己"：若 PRD 可启动、signoff 只签高风险、QA 与签核都往轻里走，收敛可能退化为 AI 自证。评估结论是——**真正的担保是四道承重墙，其余防线应按"防什么失败"评估，而非按"负担多大"评估**。

## Decision

### 1. 四道承重墙固化（不可配置，任何 skill 不得绕过）

1. **测试前置**：契约（REQ → 测试）在实现前锁定；REQ 是测试唯一出生地。
2. **实现者对测试只读**：AI 不能改契约来刷绿灯——结构性防作弊。
3. **PRD 对齐子代理**：测试全绿 ≠ PRD 意图落地（`build-progress.md` 可追溯性表 + 对齐子代理，ADR 0003 #6-7）。这是唯一在 BUILD 内部针对"为绿而绿"的防线，快速收敛下 PRD 更可能不完整，它的重要性不降反升。
4. **初衷锚点**：问题陈述（用户痛点）是回流判断基准——防"越迭代越偏离初衷"（单人快速迭代的最大风险）。

### 2. 候选减项（留账，暂不落地，试用后验证）

- REFLECT 知识沉淀减薄（值得才写，不再每 story 全量更新 7 个全局文档）。
- capability/entity + `business-capabilities.md` 变可选（bootstrap 开关，多能力域才启用）。
- `requirements-v{N}.hash` 放宽。
- bug `blast-radius` 阈值放宽。

### 3. 防线分级方向（留账，暂缓）

按"**人投入的注意力**"分级触发防线（人越不看的地方，越需要机器防线），而非 simple/complex 一刀切——simple 不代表为绿而绿风险低，恰恰是用户可能只瞄一眼签核。暂缓落地，等试用反馈。

## Consequences

- **承重墙固化**是快速收敛的安全下限：在压缩流程、减少人确认点的同时，保证"凭什么相信跑出来是对的"仍有四道不可绕过的担保。
- **候选减项与防线分级**不落地为机制；本 ADR 仅作决策记录，试用后的新感受将驱动新的 ADR 决定取舍。
