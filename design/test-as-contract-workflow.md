# 测试即契约：AI 自主开发流水线

> 状态：方法论原型 v0.1（经一轮对抗式访谈拷问成形，2026-06-19）
> 一句话：**人把需求说到机器可验的精度，AI 在测试构成的契约里自主实现；人不直接改代码，而是通过测试和需求来纠错。**

---

## 0. 它要解决什么

把"AI 自主写代码"做成可信的关键，不在于让 AI 写得更快，而在于**人怎么纠错**。

直接改代码 / 直接命令 AI 改代码，都会被 AI 的误解吞掉——它当初就是误解了你的意图才写错的，你再用自然语言纠正，它可能继续误解。本方法把人的纠错接口换成**测试**：人只负责裁定"什么算对"，把这个判断编译成机器可验证的契约，AI 在契约内自主迭代。

人的工作因此整体**上移到规格层**。PRD/UX 的精度，直接决定下游能自动化多少——这是整套方法的杠杆点，也是它的全部成本所在。

---

## 1. 主链路（一次一个功能，串行）

```
需求洞察（对抗式访谈，AI 盘问人）
   │  ← 在写任何代码之前，逼出隐含需求 / 边界 / 自相矛盾
   ▼
PRD / REQ（每条带 ID，机器可回溯）+ HTML UX（思考工具）
   │  ← 进循环前：完整性体检（批判者扫“缺了哪些状态”）
   │  ← 双轨收割 HTML：
   │       行为/结构决策 → 转写成文字 REQ（驱动测试）
   │       视觉/交互决策 → HTML 作为视觉参照，挂在 REQ 上（人眼验收基准）
   ▼
测试作者智能体：从 REQ 写“前置验收测试”（循环的靶子）
   │
   ▼
【门 1】人审并签字"断言"          ← 人最重的一次介入；不签字不准往下
   │
   ▼
实现者智能体：对着测试自主磨        ← 中段全自主，人退出
   │   · 内循环只跑单元测试（毫秒级），且每轮跑【全套】单元 → 兜住跨功能回归
   │   · 测试对实现者只读；代码差异一旦碰测试文件 = 本轮作废
   │   · 烧完 N 轮（轮数上限）还不绿 → 逃生口（见下）
   ▼
全单元绿 → 慢外门：浏览器 E2E / App E2E（不进内循环，仅收尾/合并时跑）
   ▼
【门 2】人验观感（对着 HTML 参照看手感）
   │   · 过   → 完成
   │   · 不过 → 判性质（两者都回流【门 1】，绝不在此手改代码）：
   │            偏离已有 REQ   = 缺陷      → 该 REQ 验收标准漏了此场景 → 补验收标准增量 → 测试随之长出
   │            REQ 没写 / 写错 = 需求变更  → 补 / 改 REQ → 测试重生
   │            （两条都先动 REQ；AI 起草 REQ 增量，人只签字认增量）
   ▼
 完成（"可合并" = 全套绿，不是功能自己绿）
```

**逃生口（中段卡死）**：实现者有轮数上限。烧完还不绿，停下来上报，且只准两种姿势：
- "我实现不出来，诊断如下" → 升级给人 / 换更强模型。
- "我怀疑断言 X 自相矛盾 / 不可满足，证据如下" → 路由回**门 1 让人重审断言**。

无论哪种，**实现者都不准自己改测试**。

## 2. 五条承重不变量

动了任何一条，整套方法就塌。

1. **断言归人。** 人只持有"什么算对"这一行判断；AI 持有其余全部脚手架（环境 / 夹具 / 选择器 / 模拟对象 / 数据）。AI 不得擅改断言，不得用被否决的输出反推断言。
2. **PRD/REQ 是唯一裁判，也是测试的唯一出生地。** "这是缺陷还是需求变更"靠回溯 REQ 机械裁决，不靠感觉——所以 REQ 必须带 ID、可回溯，测试反向挂 REQ ID。**没有任何测试可以脱离 REQ 存在**：连缺陷触发的测试，也是先把那条 REQ 的验收标准补细、再派生测试。这从结构上杜绝套件腐化（测试的生命周期 = REQ 的生命周期，无主测试不存在）。
3. **主观不进测试。** 行为对错由机器判（测试），观感好坏由人判（HTML 视觉参照）。两条纠错回路并存、不打架。
4. **绿灯不许撒谎。** 四层防作弊：角色隔离（测试作者 ≠ 实现者，权限互斥）+ 实现者对测试只读 + 抗特判测试（多输入 / 基于性质 / 隐藏保留集）+ 停机条件是"全套绿"而非"功能自己绿"。
5. **人的功夫上移到规格层。** PRD/UX 精度 = 下游自动化的上限。健康度指标：门 2 发现的缺口比例应随时间下降；居高不下 = 需求洞察投入不够。

## 3. 角色与权限模型

| 角色 | 能写 | 不能写 | 职责 |
|---|---|---|---|
| **人** | REQ、断言、HTML UX | （不直接写实现代码、不在门 2 手改代码） | 画靶子、签断言、验观感、裁决缺陷/需求变更 |
| **测试作者智能体** | 测试文件（脚手架）| 实现代码 | 把人签字的断言展开成可执行测试 |
| **实现者智能体** | 实现代码 | 测试文件（只读） | 在测试契约内自主迭代到全套绿 |

关键：测试作者与实现者**权限互斥**，这是"绿灯不撒谎"的结构性保证。

---

## 4. 测试分层

| 层 | 速度 | 位置 | 负责的缺陷类型 |
|---|---|---|---|
| **单元** | 毫秒级、确定性 | **内循环**，每轮全跑 | 纯逻辑 / 数据变换 |
| **浏览器 E2E** | 秒级、偶不稳定 | 慢外门（收尾 / 合并） | Web 端接线与流程 |
| **App E2E** | 几十秒~分钟、最不稳定 | 慢外门 | 原生特有的接线与流程 |

**缺陷下沉原则**：每个缺陷用"能复现它的最低层"来表达。只有非全栈跑不出来的，才允许进 E2E。这样内循环快、E2E 套件薄。

**多端约定**：同一功能在 web / app 各实现一遍（不一定同时有两端）。纯逻辑应抽成平台无关的核心层、共享同一套单元测试；只让平台外壳 + 各自 E2E 分开，避免同一算法两端各写各错各修。

## 5. 测试的生命周期：写 / 更新 / 删

> 三个分叉已定版（2026-06-23）：断言形式 = **例子表 + 不变量**；快照**默认禁用当测试预言**（只当变更探测器，每个值人过目）；采纳**变异测试**作“无用测试”探测器（周期跑，不进内循环）。

**统一心智：一条测试 = 断言（人持有）+ 脚手架（AI 持有）。写 / 更新 / 删三个操作全部由 REQ 闸门控制，并有一根抗作弊线贯穿。**

### 5.1 怎么写

- 人产出并签字的最小单元是**断言**，不是整个测试文件。两种承载形式：
  1. **例子表（输入 → 期望输出）**：人填期望输出列，这一列就是测试预言；AI 无法伪造 → 抗作弊、抗循环。
  2. **不变量**：对任意输入都成立的性质（如“分摊总和 = 原值”），挡住针对单例硬编码特判。
- **抗循环红线**：期望输出只能来自人的意图 / REQ，**绝不能从“跑一遍当前代码”抄**——否则 AI 的输出成了自己的测试预言。由此**默认禁止快照当测试预言**；快照仅作变更探测器，且每个值人过目。
- AI 把每条断言展开成可执行测试（测试准备 / 夹具 / 选择器 / 模拟对象）。
- **分层**（见 §4）：能在单元层表达就别上 E2E（缺陷下沉）。E2E 的断言 = "用户走完流程 X、看到结果 Y"，中间步骤是脚手架，最终可观察结果才是断言。

### 5.2 怎么更新

**铁律：永远不为了让测试变绿而改测试。** 合法的更新触发只有三个：

| 触发 | 改什么 | 要签 REQ 吗 |
|---|---|---|
| 需求变更 | REQ 意图 / 验收标准变 | 是 |
| 缺陷（标准漏了此场景） | 补 REQ 验收标准增量（AI 起草、人签增量） | 是 |
| **覆盖洞（标准全、测试缺）** | **只补测试** | **否**（能追溯到已签标准即可） |

- **机制**：每条测试记录 **REQ-ID + 验收标准版本（哈希）**。标准一改 → 版本不匹配的测试自动标“过时待重生”；AI 重做脚手架，**断言 / 期望输出的任何变化都要人重新签字**。
- **覆盖洞的试金石**（区分第 3 行与第 2 行）：定这条新测试的期望输出，**需不需要人做一个"什么才算对"的新判断**？
  - 不需要（能从已签标准机械推出）→ 自由补，不签字（例：标准写了"空 / 单 / 多"，AI 当初漏了"空"，补上即可）。
  - 需要（得新拍一个对错）→ 你在新增断言 = 在补标准 → 写进 REQ 并签字，哪怕 REQ 意图没变。
- **加与改**：
  - **添加**守护已有标准的测试 → 永远允许（只收紧网）。
  - **改脚手架**（修不稳定选择器 / 夹具）→ AI 随便改，不涉 REQ。
  - **改断言 / 期望输出** → 测试当初写错就按标准改对（人确认）；想放松又无 REQ 依据 = **挪门柱，禁止**。
- **谁、何时**：补测试是**测试作者 / 人**的活，**不能是实现者在循环里**（实现者对测试只读）——补测试只收紧网，放循环外安全。

### 5.3 怎么删

纯粹派下 **测试存活 ⟺ REQ 存活**，删除也是 REQ 驱动。"无用测试"分三类，后两类更阴险：

| 类型 | 表现 | 危害 |
|---|---|---|
| 孤儿 | REQ-ID 指向已不存在的 REQ | 纯粹派下应为空，是安全网 |
| 同义重复 | 多条测同一行为 | 维护噪音 |
| **永真 / 空洞** | 过度模拟对象，改坏实现也不红 | **比没用更坏——给假绿灯** |

- **检测三件套**：① **孤儿扫描**（REQ-ID 解析不到活 REQ）；② **变异测试**（变异实现，仍绿 = 没守护任何东西 → 删或加强，soflow 没有这层）；③ **按验收标准覆盖**（每条标准 ≥1 测试守护；超出的多余 = 合并候选）。同一张"标准 × 测试"覆盖图，补洞与删冗两头都靠它。
- **删除权限对称于写**：删测试是 REQ 级判断（这条标准还需不需要守护），**AI 提议 + 给证据，人签字批准**。绝不让 AI 自由删——它可能删掉正好抓它缺陷的那条（作弊的反向版）。

### 5.4 一根贯穿三操作的抗作弊线

- **写**：期望输出永远来自人意图，绝不来自当前代码输出。
- **更新**：测试变更永远追溯到 REQ 变更或已签标准，绝不追溯到"让它变绿"。
- **删除**：永远要证据 + 人签字，绝不让 AI 悄悄删掉抓它的测试。

## 6. 决策日志（每道门背后的"为什么"）

- **问题 1 测试的双重身份**：选“既是精确沟通契约、又是回归资产”。因为真正痛点是自然语言纠错会被曲解（沟通），但既然写了就顺手沉淀成防回归资产。代价：需机制区分永久契约与临时纠错，否则套件腐化（→ 留账①）。
- **问题 2 谁写测试**：人持断言、AI 持脚手架。若 AI 全包，它会用"自己的误解"写测试并刷绿，纠错沦为自欺。
- **问题 3 写不成测试的问题**：客观行为走测试，主观感知不走测试。强行全塞进测试通道，只会得到一堆假测试或主观问题无出口。
- **问题 4 缺陷还是需求变更**：靠回溯 REQ 机械裁决，不靠感觉。代价：PRD/UX 必须结构化带 ID（用户认同——"不在 PRD/UX 花功夫，代码就没法完全自动化"）。
- **问题 5 防 AI 作弊刷绿灯**：角色隔离 + 只读 + 差异检查 + 抗特判测试。"自主对测试迭代"的头号翻车点是 AI 糊弄测试（改测试 / 硬编码 / 模拟掉真逻辑）。
- **问题 6 三层谁进循环**：单元进内循环，E2E 当慢外门，缺陷尽量下沉。否则每轮等几分钟、被不稳定误判，自主迭代不成立。
- **问题 7 HTML UX 的权威**：作为代码扔、作为视觉参照留；行为决策转 REQ，视觉决策挂 HTML。既尊重"HTML 不是最终实现"，又不让视觉决策蒸发。
- **问题 8 测试先写还是后补**：前置验收测试为主（循环第 1 轮就有靶子），反应式补测为辅且多半本质是需求变更。把"发现问题→写测试"从主路径降级为例外。
- **问题 9 人站哪几个点 + 失败出口**：人在边界（门 1 签断言、门 2 验观感），AI 在中间；逃生口按轮数卡。买"中段全自主"必须付"门 1 人审断言"这笔钱。
- **问题 10 跨功能回归 + 并行**：停机条件升级为“全套绿”，快单元层每轮全跑兜回归；本期按串行验证，并行的隔离+合并门推迟。
- **问题 11 PRD 怎么浇**：对抗式访谈 + 进循环前完整性体检。把缺口发现成本从最贵的门 2 挪到最便宜的访谈期。
- **问题 12 PRD 不可能一次想清（双挡）**：一挡探索（HTML，无测试，随便推翻）/ 二挡固化（测试锁定）；跨越线 = “即将被依赖 / 不再推翻”。方法不是要你一次想清，而是只把"停止移动"的东西固化。详见 `workflow-framework.md` §3。
- **问题 13 四层真理流 + 纠错向上**：PRD → REQ → 测试 → 代码，真理只向下流；纠错只回到“出错的最高那一层”，低层禁止就地打补丁。
- **问题 14 测试生命周期三操作**：写（断言归人=例子表+不变量，禁快照当测试预言）/ 更新（三触发器，唯一合法触发是 REQ 变或补已签标准的覆盖洞，绝不为变绿改测试）/ 删（孤儿扫描 + 变异测试 + 标准覆盖图，AI 提议人签字）。见 §5。
- **问题 15 覆盖洞 ≠ 缺陷**：标准写全但测试没派生完整时，可不动 REQ 直接补测试；试金石 = 定期望输出需不需要人做新的对错判断。
- **对标 soflow**：参考项目缺的不是测试，是"把测试预言锚定在人持有、抗作弊的断言上"；我们补的是这层"测试信任层"。见 `workflow-framework.md` §7。

## 7. 留账（① ② ⑤ 已结，③ ④ 本期主动推迟）

1. **测试套件防腐 —— 已结（2026-06-19，纯粹派）。** 取消 `@regression` 临时通道：测试的唯一出生地是 REQ 的验收标准，生命周期 = REQ 的生命周期，无主测试不存在，套件结构上不会腐化。连缺陷也走"补 REQ 验收标准增量 → 测试随之长出"（AI 起草增量，人只签增量），不存在"绕过 REQ 直接补测试"的近路。代价：每次纠错都要回规格；靠"AI 起草、人只签小增量"把摩擦压到可接受。
2. **E2E 不稳定 / 腐烂 —— 已结（2026-06-19，顺优先）。** 红灯默认阻断；有界重试只做分类不做治疗——稳定红 = 真失败走门，状态翻转（时绿时红）默认放行合并但强制开限时不稳定单。两道刹车：(a) 同一条测试反复翻转到阈值 M → 转为阻断、强制分诊（封住"真竞态静默上线"的赌注）；(b) 全局翻转率当可见健康指标。不稳定测试归测试作者智能体修（持有 E2E 脚手架；疑似产品侧竞态则升级回门 1，不准把测试改松盖红）。修复批量化（攒到阈值 / 定时集中修），不在循环中途即时修，省词元。隔离区有时限、可见（每条挂 REQ，隔离 = 该 REQ 暂失 E2E 守护），永不静默转永久。残余风险：翻转到修好之间存在间歇缺陷溜入的窗口，封顶阈值限其频率、不消其存在——上线高危功能需调紧阈值。
3. **并行**：本期按串行。多功能 / 多智能体并行所需的工作树隔离 + 合并门，待启用时设计。
4. **逃生口精化**："连续 K 轮绿灯数没涨就停"这个比纯轮数更省词元的信号，留作后续叠加。
5. **非功能需求 —— 已结（2026-06-19）。** 不整体排除，套问题 3 统一规则：凡能写成"带可验证阈值 / 规则的 REQ 验收标准"就走同一套机制（性能阈值、鉴权规则、可访问性静态检查 都只是 REQ 的另一类验收标准；性能与重安全测试归慢外门，不进内循环），写不成的（开放式安全姿态、主观读屏体验）按问题 3 归人判 / 专家门，不在自动循环内。阈值本身是人持有的断言（问题 2）。

## 8. 与本项目的关系
