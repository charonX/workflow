# demand-insight

## 何时调用

用户说"我要做一个新功能"、"我想重构这个"、"帮我看看这个需求"时。如果用户已经给了很完整的 PRD，直接调用 `/to-prd` 合成，不必访谈。

## 输入

- 用户的初步想法（一句话到一段描述）
- 可选：现有代码路径、相关工单、竞品参考

## 输出

`.aiassist/stories/<id>/interview-notes.md`

## 执行步骤

### 1. 开场：先给出假设与置信度

在问任何问题之前，写下你对用户意图的**一句话假设**和一个诚实的**置信度数字**（0–100%）：

```
HYPOTHESIS: 你想要一种方式在 standup 回答"我们进展如何"，"dashboard"是你想到的传统答案。
CONFIDENCE: ~30% — 缺少：给谁用、metrics 指什么、成功标准是什么
```

规则：

- 置信度低于 ~70% 时，必须在同一行给出理由：还缺什么、什么还没澄清。
- 这个数字迫使你诚实。如果你写 80% 却无法预测用户接下来三个问题的反应，那这个数字就是错的。
- 把这个假设展示给用户，作为访谈的起点。

### 2. 确认范围

用一句话复述用户要解决的问题，请用户确认或修正。如果用户描述的是多个独立子系统，先帮其分解，再聚焦第一个子系统。

### 3. 探索项目上下文

在深入提问之前，快速了解当前系统状态：

- 扫读项目 README、CLAUDE.md、现有代码结构。
- 查看最近提交、相关 issue/工单、竞品参考。
- 识别与本次需求相关的现有模块和约束。

把发现的约束带到后续问题中，不要脱离上下文凭空提问。

### 4. 轮询澄清（round-by-round frontier）

> **默认按轮批量;偏好一次一问可覆盖。** 若用户在目标项目全局 `CLAUDE.md` 写了 `When grilling, ask one question at a time.`,则本环节改为单题串行节奏(每次只问一个尖锐问题,等回答再问下一个)。批量与一次一问不互斥——批量是默认,偏好可覆盖。

按**轮**推进访谈，一轮 = 整条 frontier + 等待回答。**frontier = 所有前置已满足、现在可以问的问题**（不依赖你还没听到的答案）。每轮把整条 frontier 一次问完，编号 + 给出推荐答案；用户回答重塑决策树后，重算 frontier 进下一轮。

> 来源于 mattpocock `grilling` 的 round-by-round frontier 模式：批量抛出的是一批**互不依赖**的问题，依赖别的答案的问题留到更晚的轮次，不会提前猜。

**每轮展示思考再提问**：在抛出一轮问题之前，先输出：

1. **我当前的理解**：基于已回答内容和项目上下文，你提炼出的用户意图/约束/风险。
2. **为什么本轮问这些**：这一批问题对应哪些未澄清的假设，不澄清会导致什么后果。
3. **我看到的选项/倾向（可选）**：如果有明显更优方向，给出推荐并说明理由；如果没有，就说不确定，需要用户输入。
4. **编号问题 + 每题推荐答案**。

**使用 Q + GUESS 格式提问**（每轮每个问题都带）：

```
Q1: <聚焦问题>
    GUESS: <你对答案的假设，以及产生这个假设的推理>
Q2: <聚焦问题>
    GUESS: <...>
```

为什么每题附带 GUESS：

- 用户纠正一个错误假设的速度，远快于从零生成答案。
- 它迫使你暴露自己的假设，而暴露假设正是访谈要解决的问题。
- 降低用户"附和式同意"的风险：批量抛题更容易诱发"都行"式全选，每题附推荐答案把被动点头变成对具体提议的回应；要 visibly 愿意被推翻，偶尔朝你预期用户会反驳的方向猜。

**哪些问题进本轮 frontier，哪些留到下一轮**：

- **进本轮**：不依赖任何本轮其他问题的答案、前置已由之前的回答满足的问题。
- **留到下轮**：答案依赖本轮某个还没听到的回答的问题——那是"更晚的轮次"，不是本轮。不要提前把可能无效的假设放进问题里。
- 保持一份"待探索维度"清单（谁 / 为什么 / 边界 / 矛盾 / 野心 / 可行性 / **本质**），据此挑选本轮 frontier 该覆盖的维度。

**事实自己查，决策问用户**：

- frontier 里需要环境事实（文件系统、工具等）的问题，派子 agent 去查，不要为你能自己查到的东西问用户。
- **不阻塞本轮**：运行中的探索算"未决前置"，只有依赖它的下游问题等子 agent 报告，其余 frontier 现在就问。

**其他规则**：

- 遇到"大概"、"可能"、"到时候再看"等模糊回答，立即追问到可验证的精度；追问本身只问一个点，不扩大成新的一轮。
- 当用户回答里出现隐含假设时，先停下来确认："你刚才默认了 X，是这样吗？"得到确认后再继续。

**探测"想要 vs 应该想要"**：

最危险的答案是用户给出"听起来像正确答案"的东西，而不是他们真正想要的。警惕：

- 答案匹配最佳实践话术（"我要它可扩展"、"干净架构"）但没有具体细节。
- 答案诉诸惯例（"大多数人这样做"、"标准做法"）。
-  phrases like "我应该……"、"我大概应该……"、"好的工程实践说……"。
-  buzzwords 作为目标："现代"、"可扩展"、"健壮"。

当听到这些时，问：

> *"如果不用向任何人解释，你真正想要什么？"*

这个问题通常比前五个问题更有效。

**第一性原理问题示例**（在讨论陷入"竞品这样做""我们习惯那样做"时使用）：

- 如果抛开现有产品、竞品方案、技术限制和用户习惯，用户要完成的那件"工作"本身是什么？
- 他们今天是怎么做的？为什么现有的替代方案不够？
- 哪些约束是真实的物理/业务约束，哪些只是"我们一直这样做"？
- 如果这是一个全新的领域，没有任何先例，你会怎么解决这个痛点？

### 5. 95% 置信度停止条件

继续轮询循环，直到你能对下面这个问题回答"是"：

> *"我能预测用户对我接下来三个问题的反应吗？"*

- 如果可以，说明你们已经达成共同理解，停止访谈，进入步骤 6 呈现确认方向。
- 如果不可以，继续问下一个问题。
- 如果已经多轮仍无法预测，停下来告诉用户："我已经问了 X 个问题，仍然无法预测你的反应，说明某个基础假设缺失。我们要不要退一步？"

### 6. 提出 2-3 个方向/方案

当核心问题、用户画像、关键边界、隐含假设都基本清晰后，给出 **2-3 个可能的解决方向**，每个方向包含：

- **一句话概括**
- **适用场景**
- **主要取舍**（成本、风险、速度、可扩展性等）
- **你的推荐和理由**

不要只有一个方案。多个方案的对照是暴露隐藏偏好的最好方式。

### 7. 呈现设计方向并确认

按复杂度分块呈现推荐方向，使用用户的语言：

```
我现在认为你想要：

- Outcome: <一句话成果>
- User: <谁受益>
- Why now: <什么变了>
- Success: <怎么算成功>
- Constraint: <最紧约束>
- Out of scope: <明确不做什么>

Yes / no / refine?
```

要求：

- Out of scope 不可省略；一半的分歧来自对"不做什么"的沉默分歧。
- 用户说"否" → 回到步骤 4 重新澄清，或回到步骤 6 换方向。
- 用户说"是" → 进入步骤 8。
- **以下回答不算"是"**：
  - "Whatever you think is best." → 用户在委托，说明他也不确定。重新用两个具体选项框定选择。
  - "Sounds good." → 模糊。追问："有什么你要调整的吗？"
  - "Sure, let's go." → 往往是礼貌退出。同样追问。

### 8. 记录洞察

把最终确认的方向和所有讨论整理成结构化笔记，**不要当场生成 PRD**。

### 9. 收尾确认

问用户：

- "还有哪些我没问到的？"
- "这个方向如果错了，最可能错在哪一层？"（为后续回流埋根因判断的伏笔）
- "现在可以生成 PRD 了吗？"

## 追问风格

- **轮询而非单问**：每轮把互不依赖的 frontier 问题批量抛出（编号 + 推荐答案），依赖问题留到后续轮次，顺序由决策树决定。
- **展示推理过程**：每轮问题前给出当前理解、提问理由和倾向推荐，让用户看到问题背后的假设和取舍，而不是只收到一串质问。
- **事实不劳用户**：能查证的事实（文件系统、工具）自己派子 agent 查，不阻塞本轮。
- 不诱导、不替用户回答。
- 用户说"大概"、"可能"、"到时候再看"时，必须追问到可验证的精度；追问本身只问一个点。
- 把隐含假设显式化："你刚才默认了 X，是这样吗？"

## 纪律

- 本 skill **不写代码**、**不生成 PRD**、**不进入二挡**。
- 只产出访谈笔记，作为 `/to-prd` 的输入。
- 如果用户中途要求直接写代码，提醒："我们先完成需求洞察，再结晶 REQ，最后才能进二挡写测试和代码。"
