# demand-insight

## 何时调用

用户说"我要做一个新功能"、"我想重构这个"、"帮我看看这个需求"时。如果用户已经给了很完整的 PRD，直接调用 `/tac-to-prd` 合成，不必访谈。

## 输入

- 用户的初步想法（一句话到一段描述）
- 可选：现有代码路径、相关工单、竞品参考

## 输出

`.aiassist/stories/<id>/interview-notes.md`

## 执行步骤

1. **确认范围**：用一句话复述用户要解决的问题，请用户确认或修正。
2. **单题循环（一次只问一个）**：
   - 每次只提 **一个** 尖锐问题，等用户回答后再问下一个。
   - **展示思考再提问**：在抛出问题之前，先输出：
     1. **我当前的理解**：基于已回答内容，你提炼出的用户意图/约束/风险。
     2. **为什么现在问这个**：这个问题对应哪个未澄清的假设，不澄清会导致什么后果。
     3. **我看到的选项/倾向（可选）**：如果有明显更优方向，给出推荐并说明理由；如果没有，就说不确定，需要用户输入。
     4. **那一个尖锐问题**：用一句话精确表达。
   - 后一个问题可以依赖前一个答案生成；不要提前把可能无效的假设放进问题里。
   - 保持一份"待探索维度"清单（谁 / 为什么 / 边界 / 矛盾 / 野心 / 可行性），按当前回答动态挑选下一个最该深挖的问题。
   - 遇到"大概"、"可能"、"到时候再看"等模糊回答，立即追问到可验证的精度；追问本身也只问一个点。
3. **显式化假设**：当用户回答里出现隐含假设时，先停下来确认："你刚才默认了 X，是这样吗？"得到确认后再继续。
4. **记录洞察**：把用户的回答整理成结构化笔记，不要当场生成 PRD。
5. **收尾确认**：问用户"还有哪些我没问到的？"以及"现在可以生成 PRD 了吗？"

## 追问风格

- **一次一问**，绝不把 3-5 个问题打包抛出；问题之间有依赖关系时，顺序尤其重要。
- **展示推理过程**：每个问题前给出当前理解、提问理由和倾向推荐，让用户看到问题背后的假设和取舍，而不是只收到一句质问。
- 不诱导、不替用户回答。
- 用户说"大概"、"可能"、"到时候再看"时，必须追问到可验证的精度。
- 把隐含假设显式化："你刚才默认了 X，是这样吗？"

## 纪律

- 本 skill **不写代码**、**不生成 PRD**、**不进入二挡**。
- 只产出访谈笔记，作为 `/tac-to-prd` 的输入。
- 如果用户中途要求直接写代码，提醒："我们先完成需求洞察，再结晶 REQ，最后才能进二挡写测试和代码。"

```markdown
...

## 用户画像
...

## 关键边界
1. ...

## 隐含假设
1. ...

## 矛盾/风险
1. ...

## 最窄的切入点
...

## 待确认问题
- [ ] ...
```
