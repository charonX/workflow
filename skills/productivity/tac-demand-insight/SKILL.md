# demand-insight

## 何时调用

用户说"我要做一个新功能"、"我想重构这个"、"帮我看看这个需求"时。如果用户已经给了很完整的 PRD，直接调用 `/tac-to-prd` 合成，不必访谈。

## 输入

- 用户的初步想法（一句话到一段描述）
- 可选：现有代码路径、相关工单、竞品参考

## 输出

`.aiassist/stories/<id>/interview-notes.md`

## 执行步骤

### 1. 确认范围

用一句话复述用户要解决的问题，请用户确认或修正。如果用户描述的是多个独立子系统，先帮其分解，再聚焦第一个子系统。

### 2. 探索项目上下文

在深入提问之前，快速了解当前系统状态：

- 扫读项目 README、CLAUDE.md、现有代码结构。
- 查看最近提交、相关 issue/工单、竞品参考。
- 识别与本次需求相关的现有模块和约束。

把发现的约束带到后续问题中，不要脱离上下文凭空提问。

### 3. 单题循环澄清

每次只提 **一个** 尖锐问题，等用户回答后再问下一个。

**展示思考再提问**：在抛出问题之前，先输出：

1. **我当前的理解**：基于已回答内容和项目上下文，你提炼出的用户意图/约束/风险。
2. **为什么现在问这个**：这个问题对应哪个未澄清的假设，不澄清会导致什么后果。
3. **我看到的选项/倾向（可选）**：如果有明显更优方向，给出推荐并说明理由；如果没有，就说不确定，需要用户输入。
4. **那一个尖锐问题**：用一句话精确表达。

其他规则：

- 后一个问题可以依赖前一个答案生成；不要提前把可能无效的假设放进问题里。
- 保持一份"待探索维度"清单（谁 / 为什么 / 边界 / 矛盾 / 野心 / 可行性），按当前回答动态挑选下一个最该深挖的问题。
- 遇到"大概"、"可能"、"到时候再看"等模糊回答，立即追问到可验证的精度；追问本身也只问一个点。
- 当用户回答里出现隐含假设时，先停下来确认："你刚才默认了 X，是这样吗？"得到确认后再继续。

### 4. 提出 2-3 个方向/方案

当核心问题、用户画像、关键边界、隐含假设都基本清晰后，给出 **2-3 个可能的解决方向**，每个方向包含：

- **一句话概括**
- **适用场景**
- **主要取舍**（成本、风险、速度、可扩展性等）
- **你的推荐和理由**

不要只有一个方案。多个方案的对照是暴露隐藏偏好的最好方式。

### 5. 呈现设计方向并确认

按复杂度分块呈现推荐方向：

- 先给整体方向（1-2 句话）。
- 再分块展开：目标用户、核心流程、关键边界、最窄切口、主要风险。
- 每块呈现后询问用户："这个方向是否符合你的预期？"
- 用户说"否" → 回到步骤 3 重新澄清，或回到步骤 4 换方向。
- 用户说"是" → 进入步骤 6。

### 6. 记录洞察

把最终确认的方向和所有讨论整理成结构化笔记，**不要当场生成 PRD**。

### 7. 收尾确认

问用户：

- "还有哪些我没问到的？"
- "这个方向如果错了，最可能错在哪一层？"（为后续回流埋根因判断的伏笔）
- "现在可以生成 PRD 了吗？"

## 追问风格

- **一次一问**，绝不把 3-5 个问题打包抛出；问题之间有依赖关系时，顺序尤其重要。
- **展示推理过程**：每个问题前给出当前理解、提问理由和倾向推荐，让用户看到问题背后的假设和取舍，而不是只收到一句质问。
- 不诱导、不替用户回答。
- 用户说"大概"、"可能"、"到时候再看"时，必须追问到可验证的精度。
- 把隐含假设显式化："你刚才默认了 X，是这样吗？"

## 纪律

- 本 skill **不写代码**、**不生成 PRD**、**不进入二挡**。
- 只产出访谈笔记，作为 `/tac-to-prd` 的输入。
- 如果用户中途要求直接写代码，提醒："我们先完成需求洞察，再结晶 REQ，最后才能进二挡写测试和代码。"
